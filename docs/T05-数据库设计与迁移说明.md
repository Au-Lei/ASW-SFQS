# T05 数据库设计与迁移说明

日期：2026-10-17。适用当前 SQLite 本机版，依赖 T02 合同和 T04 工程。

## 1. 交付与执行边界

本任务建立31个持久实体、外键、索引、检查约束、迁移、事务工具及数据库测试。正式库是业务数据源，Excel是输入和导出载体。T05初始化后只有表结构；不会自动导入295个目的地或84条已有报价，也不会改写用户Excel。

T08负责目录和既有报价的预演、确认、对账及受控迁移。T06负责完整领域校验及审核状态迁移；T07实现任务Worker；T17组合审核门禁、幂等响应、变更应用和审计。存在这些实体不代表对应业务接口已经开放。

文件入口：

| `backend/app/repositories/types.py` | 精确金额与UTC时间适配 |
| `backend/app/repositories/database.py` | 本地路径、连接配置、事务、只读健康探针 |
| `backend/app/repositories/datasets.py` | 数据集版本比较更新及逻辑快照，同事务内执行 |

依赖锁定SQLAlchemy 2.0.55、Alembic 1.20.0；完整传递依赖在`uv.lock`。本机版使用Python自带sqlite3，不另接数据库服务器。当前选择已验证的2.0系列；升级依赖应单独验证合同、迁移和SQLite事务行为。

### 2.1 目录和代码

- `destination.route_group_id`是单个非空外键，直接表达一个目的地一个当前航线，不存在多航线关联表。
- `canonical_key`唯一；改名不会改变身份键。仍需业务服务检查同港异拼写，数据库无法仅凭不同字符串识别同一港口。
- `kind`共用T02枚举。TERMINAL必须有父目的地和非空`terminal_key`，同父港的`terminal_key`唯一；禁止直接以自身为父。更深层的父子循环及粒度审核由后续目录服务处理。
- `unlocode`不设全局唯一，避免父港和不同码头被强行合并。
- 国家/地区、来源、船司分别持有独立身份。来源公开码可空；不能把来源ID或内部港码填成公开码。
- 目的地别名有范围查找索引，允许歧义；多命中需人工确认。
- `location_code_mapping`必须且只能指向目的地或起运港之一。已APPROVED的同命名空间、同供应方、同规范码映射不得存在交叠日期，即使目标地点相同也需合并或拆分期间。起止日均包含在区间内；相邻不交叠期间可以存在。NULL供应方按同一标准命名空间处理，不能绕过检查。未审批记录可以并存，不能被直接用于自动匹配。

### 2.2 原始资料及候选

- 文件SHA256为普通索引，相同内容可以属于不同批次；不能按散列删除业务记录。
- 文件在存储层只读保存的实现属于T07；本任务只建立元数据与证据定位。
- 资料组与文件、候选与识别run/资料组、证据与候选/文件须同一批次。触发器检查新增及这些引用行的更新；后续服务不得随意迁移父记录的批次。
- 原始payload、标准payload、字段出处和问题分别保存。JSON列不启用隐式就地变更跟踪，更新时赋完整新对象，如`candidate.normalized_payload = new_payload`。
- `review_state`、`match_state`、`application_state`保持独立；默认分别为PENDING_REVIEW、UNMATCHED、NOT_APPLIED。审批状态至少要求审核人、时间和已审payload散列。完整审批内容一致性和修改后重审由T06/T14服务落实。
- `model_config.secret_ref`仅存服务端密钥引用名，实际密钥留在本地环境配置；不新增明文密钥列。
- `job`只预留状态、租约、尝试次数、取消标志和结果引用，尚未实现任务认领或自动恢复。

### 2.3 正式报价和不可变修订

`quotation`代表可独立检索的一条报价方案，`quotation_revision`保存对该方案的内容修正：

1. 同一港口、不同船司、来源、费用口径、码头或有效期可以有多条quotation。起运港和目的地之间只有普通索引，没有唯一价约束。
2. 新期间另建quotation，可用`related_quotation_id`关联续期，历史期间保留。
3. 同期间改错新增revision，修订号在同一quotation中唯一。
4. `current_revision_id`非空，复合外键要求它属于同一quotation。外键延迟到提交校验，因此先分配报价及修订ID，再在同一事务插入两者即可，无需提交空壳quotation。
5. revision必须关联application，且application起运港与quotation起运港一致。其对应的快照也必须存在于同一提交结果。
6. 至少有一个数值价格；零价有效，三个NULL不是正式报价。船司、来源、币种允许未知NULL，不能因此伪造USD或UNKNOWN身份。
7. 当前修订的身份快照保留当时名称、来源和码头信息。目录更新不能重写旧revision。
8. `transit` JSON保存T02航程对象的候选值、范围、原文和未知含义；不把两个备选天数擅自转换为范围。`routing`保存有序地点及原文，周几不等于实际ETD。

数据库触发器禁止更新或删除`quotation_revision`、`dataset_snapshot`、`template_config`、`application`、`application_item`和`audit_event`，包括直接SQL。修正通过新修订、新应用和新事件表达。来源组的条件尚可审核编辑；最终历史条件必须写入revision的`conditions`及逻辑快照，不能在历史查询时重新拼接正在修改的来源组条件。

### 2.4 版本、快照与幂等

- `dataset_version`每起运港一行，业务版本从1起；尚未迁移的起运港没有该行。
- `advance_dataset`用`WHERE origin_port_id=? AND dataset_version=?`比较更新，版本递增一次，并在调用者事务内保存自包含payload及SHA256；函数不自行提交。
- payload在入库前深复制，JSON按UTF-8、键排序、紧凑分隔规范化后算散列。金额在payload中仍是十进制字符串；递归拒绝浮点值。调用方必须提供当时目录名称、航线、排序、父港关系、来源编码、报价内容等完整逻辑数据；本工具不会替调用方补齐字段。
- 快照唯一键为`(origin_port_id,dataset_version)`。快照内存有逻辑payload；外部文件只能是提交后的可重建缓存。缓存位置不要通过修改不可变快照行来补记。
- `application`唯一键分别为`(origin_port_id,idempotency_key)`和`(origin_port_id,after_version)`，保存request_hash且版本要求`after_version=before_version+1`。同key不同内容的HTTP拒绝、同key同请求重放结果，由T17在这些约束上实现。
- application复合外键确保计划的起运港一致，并要求对应after_version快照。快照外键提交时校验；应用和快照可在同一事务按需要排序插入，不能只提交应用再异步补快照。
- `export_artifact`复合外键同时锁定snapshot、起运港和数据版本，模板版本也有外键。缓存索引不唯一，保留每次请求记录。FILTERED还应核对filter_payload，不能只凭普通索引复用文件。
- 计划payload的冻结、过时判定、候选版本/hash复核、真实quotation变更及审计内容完整性属于T15—T17，T05不声明已实现这些业务流程。

## 3. 精确金额、日期与时间

### 3.1 金额

传输合同是十进制字符串；ORM接受字符串或Decimal，读出Decimal。SQLite列是BIGINT，放大10000倍保存：合成示例`"123.4567"`保存为整数`1234567`。

保持T02范围：最多14位整数和4位小数，非负。拒绝float、bool、整数作为金额参数、负数、NaN、超范围和超过4位小数，不自动舍入。NULL保持NULL，`"0"`保持0。数据库CHECK再次限制存储类型为integer及数值范围，直接写入非整数小数也会失败。

当前类型和DDL面向SQLite，不能直接切换DATABASE_URL到PostgreSQL。未来迁移到DECIMAL(18,4)时，需明确除以10000的数据转换、修改类型适配和SQLite专用CHECK/触发器，并逐项验证，避免把缩放整数误当真实金额。

### 3.2 日期

报价有效期使用DATE，ORM用Python date，数据库保存完整ISO日期，结束不能早于开始。数据库还检查ISO形状和真实日历日期（拒绝2月30日）。NULL允许未知，不把当天当作默认有效期。Excel显示月日属于后续导出格式，不删除数据库年份。

有效期口径默认UNSPECIFIED；ETD只有来源明确说明时才填写。船期星期数组、港区粒度、费用阈值等JSON内部语义仍须通过T02合同及后续领域校验，不能依赖SQL通用JSON列。

### 3.3 时间戳

ORM写入必须带时区；统一转UTC存入SQLite的DATETIME，读取补回UTC时区。展示时转Asia/Shanghai。禁止传入没有时区的datetime。UTCDateTime适配负责ORM边界，绕过ORM手写SQL的管理操作需遵守同样约定。

## 4. SQLite连接与事务

- V1仅接本机文件。相对DATABASE_URL按项目根目录解析，启动时工作目录改变不改变数据库位置。拒绝内存、网络、SQLite URI参数、其他驱动和带账号信息的连接串。
- 每次连接开启foreign_keys、WAL、10秒busy_timeout和synchronous=FULL。SQLite本机文件不放共享盘；不关闭外键来迁就循环引用。
- 关闭sqlite3旧式隐式事务行为，SQLAlchemy显式发BEGIN，使DDL、保存点及业务DML都可回滚。普通读取用BEGIN DEFERRED，写应用使用`unit_of_work(engine, immediate=True)`取得BEGIN IMMEDIATE。
- `unit_of_work`结束前flush、外层提交；异常回滚全部结果。函数内部不得自己提交。会话不能跨请求或跨线程共享。
- 不把`SELECT FOR UPDATE`当作SQLite行锁。并发依靠短的IMMEDIATE写事务、业务版本比较、唯一键和重试策略。
- destination、import_batch、source_group、candidate、mapping、change_plan、dataset_version、issue、quotation、job有ORM version乐观锁。普通ORM修改自动比较版本，过时修改抛StaleDataError。批量SQL必须自己比较预期版本并检查rowcount；不能误以为Mapper版本功能覆盖批量更新。
- 应用服务负责将锁等待、版本冲突、唯一键错误转换为适当HTTP错误。当前不新增报价写入API。

## 5. 迁移与日常命令

先按锁文件安装依赖，项目根目录运行：

```powershell
uv sync --frozen
uv run --frozen python -m backend.app.repositories.cli status
uv run --frozen python -m backend.app.repositories.cli upgrade
uv run --frozen python -m backend.app.repositories.cli check
```

默认位置为`data/app.sqlite3`，可通过本地.env的DATABASE_URL配置。status只读探查；upgrade才显式创建目录与表。网页启动、健康检查、setup脚本都不自动建表或升级。

两次迁移：

| 修订 | 内容 |
|---|---|
| `0001_core` | 31表、索引、唯一键、外键和金额/日期/状态CHECK |
| `0002_history_guards` | 不可变历史、已审代码期间排重、跨批次证据及跨起运港修订保护，共21个触发器 |

第二次执行upgrade且已在目标版本时直接结束，不清空、重新建表或导入种子。已有旧版库升级会先生成一致性备份，再把所有待升级步骤放进一个IMMEDIATE事务。失败则DDL及版本号一起回滚。

备份使用SQLite backup API，并在持有写事务时用单独只读连接读取旧库，包含WAL中的已提交内容。保存到数据库旁`backups/<库名>-<UTC时间>-<随机标识>.sqlite3`。不通过复制正在写入的主文件来假设备份完整。备份不删除、不覆盖，按需另行受控保管。

未知版本、多个迁移头、有业务表但无版本标记、向后目标，均拒绝自动升级。禁止通过stamp给未知库伪造版本；需要专门迁移策略。CLI不提供破坏性downgrade；恢复使用验证过的备份。

所有迁移DDL独立冻结，不在旧迁移中调用当前Base.metadata.create_all。后续调整必须新增迁移，不能修改已交付迁移文件。Alembic的check不是完整的SQLite CHECK/触发器审计，测试额外核对迁移CHECK名称及关键触发器行为。

### 5.1 恢复步骤

1. 停止网页后端及Worker，确认没有程序持有该数据库。
2. 用SQLite只读打开备份，运行`PRAGMA integrity_check`，应仅返回ok；核对alembic_version及所需业务数据。
3. 保留当前数据库及其WAL/SHM文件作为故障资料，不直接覆盖后继续运行。
4. 将本地.env的DATABASE_URL切换到受控目录内复制出的备份工作副本，避免直接修改唯一的备份原件。
5. 对副本先运行status，匹配兼容代码版本；如需升级，运行upgrade及check，再验证业务数据和历史快照，最后启动服务。

T30—T34进一步提供完整运营备份和恢复验收；以上为T05维护方式，不代表已实现自动备份调度。

## 6. HTTP和网页状态

GET `/api/v1/health`的stage为T05，database_status返回：

| 状态 | 含义 |
|---|---|
| NOT_INITIALIZED | 数据库文件尚不存在 |
| READY | Alembic版本标记为当前head；不表示数据已经导入，也不替代完整性检查 |
| OUTDATED | 版本标记存在但未到当前head |
| UNAVAILABLE | 文件不可读、无版本表或不是可用SQLite数据库 |

探针以mode=ro连接，不创建文件，不切换journal_mode，不迁移，异常不向浏览器泄露路径或SQL。status=ok表示Web服务可响应；判断库结构可用还需看database_status。

bootstrap仍返回quotation_status=NOT_INITIALIZED，正式报价待T08接入；目录展示仍是经过校验的种子摘要，不能误认为从正式数据库读取。网页提示调整为“正式报价尚未接入”。共享Python/JSON Schema/TypeScript/OpenAPI已同步生成。

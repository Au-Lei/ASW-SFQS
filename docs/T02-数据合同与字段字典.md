# T02 数据合同与字段字典

合同版本：1.0.0。日期：2026-10-17。适用于青岛港海运报价工具第一版。

本任务交付可执行的字段校验、JSON Schema、TypeScript类型和OpenAPI合同。尚未实现网页、数据库、识别器或HTTP服务。T01真实价格继续保存在私有样本目录；公开合同使用虚构价格。

## 1. 合同的权威来源及修改方法

| 内容 | 唯一维护位置 | 派生产物 |
|---|---|---|
| 字段、状态、金额、日期及跨字段校验 | `backend/app/domain/contracts.py` | JSON Schema、前端类型、OpenAPI模型 |
| 六个sheet及18列映射 | `config/quotation-columns-v1.json` | T03样式配置及T11导出器读取 |
| API路径、请求头及返回模型 | `contracts/generate.py` | `contracts/openapi.json` |
| 可公开重放的识别输出示例 | `contracts/examples/extraction.synthetic.json` | 合同测试输入 |

执行 `python contracts/generate.py` 更新生成文件；执行 `python contracts/generate.py --check` 检查是否忘记更新。禁止直接修改 `contracts/generated/contracts.ts`、生成的Schema、OpenAPI模型或 `config/enums-v1.generated.json`。前端后续直接引用生成类型与枚举常量，不另写同义枚举。

主开发文档早期实体草案的rate_20gp/rate_40gp/rate_40hq、currency_code、origin_id、charge_basis_summary在传输合同中分别统一为price_20gp/price_40gp/price_40hq、currency、origin_port_id、price_scope_summary；validity_basis对应validity.basis，dataset_revision对应dataset_version。数据库字段由T05映射，不把旧草案名称再作为第二套API字段暴露。

Pydantic验证与Schema由同一模型产生。复杂校验（如结束早于开始、引用悬空、审核hash）在服务端执行，不能仅依靠JSON Schema或TypeScript静态类型。当前依赖固定在 `backend/requirements-contracts.txt`；全工程和锁文件由T04建立。

## 3. 基础值、金额与日期

- 应用身份使用UUID；`record_key`、`physical_row_key`是一次提取结果内的关联键，不冒充数据库ID。
- 所有缺失业务值使用null；没有字段与字段为null在PATCH中含义不同；空串、`--`不作为规范金额。
- 金额JSON是十进制字符串，例如 `"123.4500"`，最多14位整数、4位小数，非负；拒绝JSON浮点数、科学计数法、NaN、负数、前导零以及超精度。`"0"`是明确的零，不是假缺失。
- 计算使用Decimal；SQLite存为放大10000倍的整数，PostgreSQL预期使用DECIMAL(18,4)。`scaled_money`提供合同示例。主价与附加费分别保存，不自动合计。
- 币种格式为三位大写字母，是否属于实际启用币种由后续字典验证；未知为null。附加费出现USD不能证明主价币种是USD。
- 船司和来源的ID、船司缩写、来源英文编码分别维护。未编码的价格来源导出为空，不把EMC、SITC等船司缩写填入来源。
- 日期必须是有效的 `YYYY-MM-DD`；结束不能早于开始，允许一端缺失，缺失端由后续查询显示不完整。跨年必须明确两个年份；只看到月日时保留原文，待从标题/人工证据确定年份后再规范化。
- 报价有效期按闭区间保存；日期口径默认UNSPECIFIED。ETD必须有依据，不能从项目用途推断。
- 更新时间 `source_updated_on`、上传时间（后续文件实体）、报价有效期独立。审核时间使用带时区的ISO时间戳。
- Excel写入真实日期数值并设置 `mm-dd`，不能把日期转成缺年份文本；实际Excel/WPS核验属于T11。

## 4. 目的地、代码与服务身份

`Destination`包含id、canonical_key、country_region_id、kind、parent_destination_id、英文名、中文名、route_group_id、version、active。一个目的地只有一个route_group_id；`DestinationDirectory`拒绝重复ID或canonical_key，即使试图放到不同航线也拒绝。跨批目录唯一性和父节点存在性由T03/T05处理。

识别阶段使用可未匹配的 `DestinationRef`。不要把模型提出的destination_id视为已确认匹配，后端必须检查目录和证据。码头记录需要独立ID及父港：同城的TERMINAL A、TERMINAL B可以分别报价；泛城市CITY_SCOPE不会自动等同任一码头。Alexandria ABU QIR/TMT、胡志明CAT LAI/PHUOC AN、仰光AWPT/MITT遵循同一规则。

代码分为UNLOCODE、SOURCE_SPECIFIC、INTERNAL三个命名空间。SOURCE_SPECIFIC必须有source_id；不能把五位外形相似代码当作标准UNLOCODE。具体映射版本及证据由匹配服务保存。

目的地唯一归属不等于目的地唯一报价。船司、来源、码头、运输服务、路径、费用口径、有效期不同，都可能是不同报价；未知身份不是相等身份。泰国CKV2与VTX5即使港口和价格相同也保留服务差异。

## 5. 提取结果合同

`ExtractionOutput`是识别器/模型与后端之间的边界，包括：

| 字段 | 含义 |
|---|---|
| schema_version | 当前固定1.0.0 |
| document_context | 原始标题、源更新时间、起运范围原文和整份资料有效期 |
| records | 按目的地与服务展开的记录；保留physical_row_key解释一行多港 |
| groups | 原资料国家块/区域块，包含group_key、record_keys和证据 |
| conditions | 条款原文、范围、关联键、例外目标、金额/币种/计费单位/付款原文 |
| evidence | 文件和单元格/图片/文字位置及可读原文 |
| issues | 识别时发现的疑点，不包含审核/解决权限 |

每条record保留origin_raw、destination、carrier_raw、currency、service_raw、validity、schedule、routing、price_profiles、condition_keys、field_provenance、issues。记录有效期未填写时并不由模型校验器悄悄复制文档日期；标准化器只能在范围证据明确时继承并补出处。

`record_key`、group_key、condition.key和evidence.id各自唯一；任何条件/分组/证据引用必须可解析。profile_key在同一record内唯一。PROFILE级条款目标写 `record_key/profile_key`，避免不同物理行使用同一价格口径名后范围混淆。DOCUMENT目标使用 `DOCUMENT`；GROUP使用group_key；RECORD使用record_key；CONTAINER使用20GP/40GP/40HQ。容器级/文档级例外如需精确到某个目的地，应拆成相应record级条款，不能猜测范围。

模型不返回APPROVED、APPLIED或问题RESOLVED等服务端状态；多余字段会拒绝。服务端仍必须校验文件属于当前批次、证据坐标真实、ID是否允许、目录匹配和出处是否可靠，Schema通过不代表识别正确或业务审批通过。模型若不支持完整Schema，由适配器裁剪约束提示，但后端仍按完整模型验证，不降低正式合同。

### 5.1 多价格口径与原始价格单元格

每个 `PriceProfile` 保存profile_key、原列标题label_raw、purpose、container_binding、cells、container_map、evidence_ids。purpose默认UNSPECIFIED；不自动决定拿价、对客价或结算价的业务用途。

SITC四种profile分别为LEFT_QUOTE、G_KEY_ACCOUNT_SETTLEMENT、R_QUOTE、R_SETTLEMENT。后续其他来源可以使用其他key，不把这四个名称当成所有资料通用的固定菜单。

| kind | 结构和行为 |
|---|---|
| LITERAL_COMPONENT | raw_text + 十进制amount + qualifier_raw；“含BY”“含LSS”“不含”保留原意 |
| REFERENCE_PLUS_ADDON | reference_raw + addon + raw_text；amount只能为null，V1不计算基价 |
| PAIR_UNASSIGNED | raw_text + tokens；没有确认的柜型分配，amount只能为null |
| MISSING | 原文可为null或`--`，amount只能为null |

cells的key是来源列标识，不能当柜型。只有EXPLICIT/CONFIRMED绑定才可设置container_map。黄色列只有并排两个数字不能自动绑定柜型；R列的 `345/456`保留未分配双值。主价缺币种保留null；LSS自己的USD单独保存。

确认来源列为20GP和40GP/HC时，`derive_two_prices`生成40GP=40HQ，40HQ出处为RULE_DERIVED、rule_id为TWO_PRICE_20GP_40FT_V1，并包含证据ID；仅40HQ明确时不补40GP。若原文分别列出三种柜型，就按三列原值，不调用两价规则。

### 5.2 船期、路径、证据和条件

星期使用整数1—7（周一至周日），保留班期原文和service_binding。定期星期不是某次实际ETD。航程 `2/4`可保存为ALTERNATIVES，但不自动变成2—4天区间，服务/目的地对应不明时不能承诺其中一个值。

Routing.status为UNKNOWN、DIRECT、TRANSSHIPMENT；DIRECT必须有POL和POD两个节点，TRANSSHIPMENT至少三个节点；UNKNOWN不会默认直达。来源节点未确认时可只保存raw_text。

Evidence包含id、file_id、field_path、original_text和location。XLSX_CELL包含sheet_name和cell_range；IMAGE_REGION包含page_no及原图方向的归一化bbox `[x0,y0,x1,y1]`，不得拿缩略图像素直接作为原图坐标；TEXT_SPAN是从0开始、右侧不包含的字符区间。OCR无法给出精细单元格时可以给较大且真实的区域，不能虚构精确位置。

字段出处Provenance包含raw_value、normalized_value、origin、evidence_ids、rule_id、confidence。EXPLICIT和RULE_DERIVED必须有证据；后者还必须有rule_id。confidence是0—1识别置信度，不是审批状态；人工补充MANUAL仍需在审计服务登记操作者。

DG、LSS、超重条款、异常附加费缩写、排除五港等条件均保留原文和范围。没有明确单位、门槛边界或费用定义时不得结构化成已确认费用，也不得计算全包价。印度块包含尼泊尔目的地时保留COUNTRY_GROUP_CONFLICT问题，不无条件继承印度国别。

## 6. 候选、审核与PATCH

Candidate区分原始raw_payload、规范normalized_payload、field_provenance、issues与三种状态。raw_payload用于保留提取上下文，不承担正式字段职责；附件本体独立存储。

| 枚举 | 值 |
|---|---|
| ReviewState | PENDING_REVIEW / APPROVED / NEEDS_INFO / REJECTED |
| MatchState | UNMATCHED / SUGGESTED / CONFIRMED / OUT_OF_SCOPE |
| ApplicationState | NOT_APPLIED / APPLIED / NO_CHANGE / EXCLUDED |
| PlanState | DRAFT / READY / APPLIED / STALE / CANCELLED |
| JobState | QUEUED / RUNNING / SUCCEEDED / PARTIAL_FAILED / FAILED / CANCELLED / INTERRUPTED |
| ChangeAction | CREATE_QUOTE / UPDATE_QUOTE / LINK_EVIDENCE / ARCHIVE_QUOTE / NO_CHANGE / EXCLUDE |
| ProvenanceOrigin | EXPLICIT / RULE_DERIVED / MANUAL / UNKNOWN |
| DateBasis | UNSPECIFIED / ETD / BOOKING_DATE / GATE_IN_DATE / QUOTATION_DATE / OTHER |
| DestinationKind | SEAPORT / TERMINAL / ICD / INLAND_POINT / CITY_SCOPE / UNKNOWN |
| ExportMode | FULL / FILTERED |

状态名字由模型生成的枚举清单为准。以下是合同规则，不代表完整服务状态机已完成：

- 新候选默认PENDING_REVIEW、UNMATCHED、NOT_APPLIED、INCLUDE。
- APPROVED必须绑定当前候选version、规范payload hash、审核者和带时区时间。审核人从会话取得，不允许模型或普通PATCH设置。
- 改动业务值后version递增并重置审核为PENDING_REVIEW，清除旧审核快照；目的地变化还把match_state重置UNMATCHED。无实际变化的PATCH不新增版本。
- 已应用候选不可直接再编辑；后续更正创建新候选/修订。正式应用不能用编辑候选替代。
- `edit_candidate`只是纯内存的合同演示，数据库乐观锁、人工字段出处/审计和正式审核操作由T12/T14实现。

PATCH例子：原价20GP=123、40GP=234。

```json
{"expected_version":1,"changes":{"price_20gp":"125"}}
```

只修改20GP，40GP保持234。以下表示提出清空20GP，后续必须进入差异预览和审核：

```json
{"expected_version":1,"changes":{"price_20gp":null}}
```

空changes是无变化。服务端必须 `exclude_unset=True`，不能把默认null写回旧数据。结构字段validity、schedule、routing按整个对象替换；只传validity.valid_from时不会保留旧valid_to。前端应先取得完整对象、显示替换差异后提交。清空有效期用 `{ "validity": {"valid_from":null,"valid_to":null,"basis":"UNSPECIFIED"} }`；不接受整个validity=null。后续若需要嵌套PATCH，升级合同并新增用例。

识别输出里缺失字段不能直接当PATCH清空；标准化器先生成候选，由变更服务提出每个清空动作。

## 7. 每种动作的条件

Issue包含code、field_paths、message、affected_actions、severity、resolution、acknowledged_by、acknowledged_at。模型只可提出ExtractedIssue，不能自行解决问题。严重级别用于显示，affected_actions用于对应动作门槛，不能把所有疑点一律阻断所有操作。

| 情况 | 可保留/审核 | 正式应用 | 比较 |
|---|---|---|---|
| 缺起运港/无法确定青岛 | 可以 | 阻止 | 不能宣称青岛适用 |
| 目的地未确认 | 可以 | 阻止 | 不挂到猜测码头 |
| 未通过审核或已被修改 | 可以 | 阻止 | 仅草稿展示 |
| 船司未知 | 可以 | 允许带问题保存 | 不能声称具体船司 |
| 主价币种未知 | 可以 | 允许内部保存/导出 | 阻止跨记录价格比较 |
| 只有引用表达式、无可用数字 | 可以 | 不生成仅表达式的正式数字报价 | 不参与数值排序 |
| 来源编码未分配 | 可以 | 允许 | 保留内部来源ID与证据 |
| 非青岛、暂缓或排除项 | 可以 | 不进青岛正式表 | 系统详情保留 |

`gate_issues`提供部分门槛的纯函数；后续服务仍必须加载真实目录、检查档案状态、柜型、完整条件、计划与数据集版本。确认缺币种的问题不能自动填USD，也不能让它参与“最低价”计算。

## 8. HTTP、错误与版本合同

OpenAPI3.1文件为 `contracts/openapi.json`，基础路径 `/api/v1`。当前涵盖候选读取/编辑/审核、计划读取/应用及导出请求；上传、查询、字典等接口在对应任务实现时从共用类型扩展，不能把合同中的路径当作已启动接口。

JSON UTF-8；金额为字符串、日期为完整ISO日期、身份为UUID。客户端可传X-Request-ID，服务端生成或校验后在响应及错误中回传。修改候选使用body.expected_version，审核再提交payload_hash；不要同时维护互相冲突的If-Match和body版本语义。

应用请求必须携带Idempotency-Key，并提交expected_plan_version、expected_dataset_version、snapshot_hash。相同key和相同body重试返回原结果；相同key换body返回409 IDEMPOTENCY_KEY_REUSED。READY计划也必须重新检查其候选版本、字典/数据集版本和快照内容；不一致返回409 PLAN_STALE。

```json
{"error":{"code":"PLAN_STALE","message":"数据已更新，请重新生成变更预览","details":[{"field_path":"/expected_dataset_version","code":"VERSION_MISMATCH","message":"预览版本已不是当前版本"}],"request_id":"example-request-001"}}
```

| HTTP | code |
|---|---|
| 400 | BAD_REQUEST |
| 403 | FORBIDDEN（T04本机Host/Origin/会话边界；Host错误本身返回400） |
| 404 | NOT_FOUND |
| 405 | METHOD_NOT_ALLOWED（T04运行接口） |
| 409 | VERSION_CONFLICT / PLAN_STALE / IDEMPOTENCY_KEY_REUSED |
| 422 | VALIDATION_ERROR / ACTION_BLOCKED |
| 413 | PAYLOAD_TOO_LARGE |
| 500 | INTERNAL_ERROR |

字段路径使用JSON Pointer形式，如 `/normalized_payload/price_20gp`。错误详情不得泄漏密钥、内部堆栈或整份商业报价；具体问题与原文通过已授权资料入口查看。

payload_hash采用规范字段model_dump(mode=json)、UTF-8、键排序、无多余空白生成SHA-256。金额保留原精度字符串，因此`123.0`与`123.00`会使审核快照不同，这是保守的修改检测，不是同价去重算法。计划snapshot_hash还应涵盖字典版本、候选版本、条件与变更条目，不能复用候选hash冒充计划hash。数据库保存逻辑快照payload与hash要和应用在同一事务提交，文件缓存提交后再写（T17）。

新有效期新增独立报价；原有效期更正产生同报价的新不可变revision；明确并存产生不同quotation。current_revision_id仅选择该报价的当前修订，不抹掉其他有效期。

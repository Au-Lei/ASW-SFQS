## 2. 显式升级和启动

先停止旧Web/Worker，项目根目录运行：

```powershell
uv run --frozen python -m backend.app.repositories.cli upgrade
uv run --frozen python -m backend.app.repositories.cli check
```

T05已知结构升级到0003_jobs前自动生成一致性备份。保留旧任务，补齐执行根ID和初始进度；无租约的遗留RUNNING在Worker恢复扫描中变为INTERRUPTED，不变成成功。当前共34个业务表和26个保护触发器，原报价表和31个原有业务表保留。

Web仍按原有方式启动。在另一个终端启动Worker：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/worker.ps1
```

或直接使用：

```powershell
uv run --frozen python -m backend.workers run
uv run --frozen python -m backend.workers run --once
```

`--once`最多处理一个当前可领取任务，不等待退避中的任务到期；不等于所有队列均已清空。持续模式会等待后续任务。Ctrl+C正常停止，未完成工作不得记为成功；强制结束后由过期租约恢复。

Worker要求数据库结构READY，不自动升级或建库，不会因为Web重启自动重置任务。现有开发脚本仍管理Web和前端；Worker作为独立进程显式启动。默认仅一个有效Worker，重复启动会被数据库中的primary租约拒绝。

强制结束后立即启动新Worker时，旧租约可能尚未过期。应等待一个租约周期（默认30秒）后再启动，不通过删除租约行强行抢占仍可能有效的执行。

### 2.1 配置

| 配置 | 默认 | 说明 |
|---|---:|---|
| STORAGE_ROOT | ./data | 私有本机目录，不在前端/共用合同可服务目录内 |
| STORAGE_MAX_FILE_BYTES | 20971520 | 单对象20 MiB，流式写入及校验时执行 |
| WORKER_LEASE_SECONDS | 30 | Worker和执行租约 |
| WORKER_HEARTBEAT_SECONDS | 5 | 独立线程刷新，须小于租约的一半 |
| WORKER_POLL_SECONDS | 2 | 空队列轮询间隔 |

配置写本地.env，安装脚本不覆盖已有.env。STORAGE_ROOT使用普通本机路径，拒绝网络和链接目录；原件不会放进前端公开目录。T18会在此基础上实现批次总量、附件数、图片像素、xlsx解压/非空格等具体格式限制，不把T07单对象限额当作全部上传验证。

### 2.2 本机文件核验示例

对自行准备的合成文件运行：

```powershell
uv run --frozen python -m backend.workers enqueue-verify ./data/example.synthetic.txt --key verify-example-v1
uv run --frozen python -m backend.workers run --once
```

第一条将文件复制到私有原件存储并返回job_id，不改输入文件。相同key和相同内容重复运行复用对象及任务；相同key换内容拒绝覆盖。它是本地诊断命令，不是报价上传流程。真实使用请选择明确授权的本地文件，不使用商业资料作为公开测试样例。

## 3. 存储规则

Storage只接受二进制流，生成形如`sources/<系统UUID>/original`的键。中文文件名等显示信息由未来source_file元数据记录，不参与路径拼接。

支持sources、exports、snapshots、extraction_runs、job_results命名空间，各有固定叶名。调用者只允许系统UUID和规定命名空间；读取同样检查键的严格语法，拒绝绝对路径、盘符、反斜杠、上级目录和编码穿越。逐级检查符号链接及Windows junction，避免读写逃逸。

发布顺序：

1. 在受控temporary/<操作UUID>/payload.part中独占创建临时文件。
2. 分块读取并执行大小限制，同时计算SHA256。
3. flush和fsync完整字节。
4. 可选验证器校验完整临时文件；验证器不能偷偷改写已计算散列的内容。
5. 再核对路径，原子发布至新的最终键；Windows rename拒绝覆盖，POSIX同卷link拒绝替换并同步目录。
6. 成功后才返回StoredObject；失败只清理本次生成的临时文件及空目录，不递归删除任意路径。

默认已有键报冲突。只有显式reuse_identical且散列和大小一致时才能复用，内容不同绝不覆盖。读取核验也执行大小及散列检查，原件被外部改动会报FILE_INTEGRITY_MISMATCH。

本地存储目录必须由当前部署账户控制；路径检查不等于面向不可信操作系统管理员的沙箱。Web不挂载这些目录，任务状态也不返回内部存储键。

文件与SQLite不能共享一个物理事务：文件已发布而后续登记失败时可能留下未引用对象；进程被杀也可能留下临时文件。T07选择保留而不是冒险删除旧文件。T32清理/备份须核对数据库引用，不能按文件名猜测删除。

## 4. 队列与执行记录

### 4.1 原子入队和幂等

`JobQueue.enqueue_in(session,...)`允许T18等业务服务在自己的IMMEDIATE事务中同时登记业务记录和任务，函数不自行提交。外层失败时二者一起回滚，不依赖进程内BackgroundTasks通知。

入队使用kind、批次、幂等键的规范散列去重，另存包含payload和重试上限的request_hash。同键同请求返回原任务，同键不同内容拒绝。NULL批次也进入散列，不能利用SQL NULL唯一索引绕过幂等。

队列payload限定为小型JSON（64 KiB），应存文件/版本等引用，不存原图二进制或密钥。以后模型处理器还须固定parser/schema/prompt/model版本，不能在恢复中悄悄换解释口径。

### 4.2 表与租约

- job：保留T05身份、状态和版本，增加真实进度、可执行时间、幂等散列、retry_parent_id、execution_id。
- job_attempt：每次认领生成一个新的执行ID，同时作为随机fencing token，保存执行号、Worker身份、开始/结束时间和安全错误码。已结束的执行记录不能改写，不能删除历史。
- job_checkpoint：以执行根execution_id和item_key唯一记录成功单元及结果散列。不可变，跨执行根引用会被触发器拒绝。
- worker_runtime：primary单例租约，确保默认一个有效Worker。

认领在短的BEGIN IMMEDIATE事务中完成，只有QUEUED、未取消、次数未耗尽、退避已到期的任务可领取。队列用条件和唯一键保护，不能用SQLite SELECT FOR UPDATE假装行锁。

每次认领使用新token。心跳、进度、检查点和结束都核对Worker租约、任务租约及token；旧Worker迟到的结果不能覆盖恢复后的任务。心跳不递增用户操作version，避免单纯心跳让取消请求一直过时；进度、状态和人工控制仍受版本保护。

### 4.3 状态与重试

正常流程为QUEUED → RUNNING → SUCCEEDED。成功必须明确完成已声明单元数并返回结果，处理器无进度或缺结果不能自动成功。

暂时错误（例如TIMEOUT、RATE_LIMITED）可在同一任务下创建后续attempt：原attempt保存失败，job回到QUEUED，保留已成功检查点。默认最多3次，指数退避加随机抖动；明确Retry-After不早于服务端要求，受支持的值为0至86400秒。身份认证、格式或无处理器等永久错误直接失败。

已完成部分后出现不可恢复错误记PARTIAL_FAILED；没有成功单元则FAILED。不是把异常忽略后标成功。具体处理器应以业务文件/单元为进度单位，不能拿检查步骤数冒充已识别报价数。

POST retry只允许FAILED、PARTIAL_FAILED、INTERRUPTED、CANCELLED，创建新的job并关联retry_parent_id，旧任务结果保留。一个父任务只生成一个直接重试子任务，重复请求返回同一子任务；子任务再次失败应对该子任务重试。成功任务不通过retry重新执行，需要建立新的处理请求。

同一执行根的成功检查点可跨自动尝试和显式恢复复用。处理器必须检查缓存引用是否仍有效；当前VERIFY_FILE即使有检查点仍重新核对原件完整性。重新解析不得覆盖人工候选，未来处理器须创建新的extraction_run。

### 4.4 中断恢复

Worker启动和轮询时检查过期租约，将遗留RUNNING及对应活动attempt记INTERRUPTED。租约仍有效的任务不会被另一个进程随意认作中断。中断不会自动宣称完成，也不自动重新识别；用户显式retry后才恢复。

心跳在独立线程持续执行，长耗时I/O期间仍刷新租约。租约丢失后停止后续提交，旧进程不能继续写检查点或标成功。强制终止测试使用本测试创建的子进程，验证真实跨进程恢复，而非只修改内存状态。

这是一套至少一次执行、结果幂等的基础设施，不能保证外部模型调用恰好一次：若请求已发出但响应尚未持久化时崩溃，重试可能再调用。正式报价写入必须通过T17应用事务和幂等键；当前Worker没有正式报价写入处理器。

### 4.5 取消

QUEUED取消立即进入CANCELLED。RUNNING取消先持久化cancel_requested；处理器在检查点/文件边界协作停止，已发出的不可取消调用可等待返回。

取消标志被发现后不再提交新的成功单元，最终不会记SUCCEEDED；已返回结果可以只作为取消任务记录保留，状态接口不会把它当作可用成功结果，也不会推进审核或正式应用。已完成单元及历史不删除。

没有声明能强制中止任何第三方网络库。T23必须配置真实网络超时并实现适配器取消；用户取消不以立即杀死整个Worker代替。

## 5. HTTP合同

| 接口 | 行为 |
|---|---|
| GET /api/v1/jobs/{id} | 真实状态、版本、单元进度、执行次数、安全错误码、重试子任务ID |
| POST /api/v1/jobs/{id}/cancel | body为expected_version，取消排队/活动任务 |
| POST /api/v1/jobs/{id}/retry | body为expected_version，返回新建或已存在的重试任务 |

先GET /bootstrap建立有效本机cookie。GET任务也验证该cookie，POST还由既有边界检查受信Origin及对应X-CSRF-Token。运行OpenAPI与生成合同均声明这些要求；这仍是本机单用户保护，不是局域网企业账号系统。

状态不包含payload、原始异常、密钥、物理路径、内部存储键、租约owner/token和原始result_ref。不存在404、版本冲突409、状态不支持422、结构未就绪503。未迁移时返回明确错误而不偷偷创建数据库。

状态只报告已知progress_done/total，不提供伪造百分比或预计剩余时间。前端以后可每2秒轮询，离开页面停止轮询不会停止任务。T07暂不增加上传和审核网页，现有页面仍明确这些功能待接入。

# T06 领域规则与状态校验说明

日期：2026-10-17。对应编码计划T06，依赖T02字段合同、T05数据库基础。

## 1. 范围和入口

本任务提供可执行的纯领域规则，服务于后续候选编辑、审核、计划和应用。函数不读写用户Excel，不调用模型，不直接写数据库或生成正式报价，也不新增HTTP业务接口。

| 模块 | 用途 |
|---|---|
| `backend/app/domain/values.py` | 不可变MoneyAmount、完整日期、日期适用性、指定柜型取价 |
| `backend/app/domain/validation.py` | 字段出处、证据/条件引用和按动作分别检查的Issue |
| `backend/app/domain/candidates.py` | 人工编辑、确认字段、纠正出处、目的地匹配和审核命令 |
| `backend/app/domain/transitions.py` | 审核、匹配、应用和计划状态允许的迁移 |
| `backend/app/domain/errors.py` | 稳定DomainError及字段/问题代码 |
| `backend/app/domain/contracts.py` | 共用DTO、枚举、基础跨字段校验和生成入口 |
| `tests/domain/test_domain.py` | 54项合成业务测试 |

T02的`contracts.edit_candidate`、`contracts.gate_issues`保留以回放既有合同测试，已明确标为局部演示工具。真实编辑和审核必须调用本任务的新命令及完整门禁，不能将旧工具直接作为写接口。

## 2. 金额和柜型

### 2.1 精确金额

MoneyAmount是不可变对象，接受十进制字符串或Decimal，内部使用放大10000倍的整数；SQLite继续使用T05缩放整数列，传输仍使用字符串。

- 最多14位整数、4位小数，非负，不自动舍入。
- 拒绝float、bool、整数金额参数、指数字符串、NaN、Infinity、负零、超范围和超精度。
- NULL通过调用者表示未知；MoneyAmount本身不把未知转成0。
- 合成示例`"12.3400"`与Decimal("12.34")代表相同金额；规范wire输出为`"12.34"`。
- 候选DTO保留原十进制字符串格式用于审核；MoneyAmount的数值相等不意味着未经审核修改候选的字符串表达。
- `scaled_money`及SQLite读回转换不依赖全局Decimal计算精度，避免其他模块降低precision后错误舍入金额。入库、读回和最大精度用例均有验证。

### 2.2 指定柜型

共用ContainerType枚举仅含20GP、40GP、40HQ，并已生成TypeScript类型。`price_for_container`只读取所选柜型，缺价返回None，明确零价返回金额0。

不把40FT、40HC等来源表头直接当作查询柜型。来源别名映射属于T20标准化，必须先确认含义。只有40HQ有价时不自动补40GP。

`derive_two_prices`要求确认参数实际为布尔True并带证据；字符串“yes”或整数1不算确认。补齐40HQ的唯一已注册规则为TWO_PRICE_20GP_40FT_V1。完整出处校验再次检查：适用字段是price_40hq，20GP/40GP有值，40HQ与40GP一致，原推导输入与40GP一致，证据在当前批次内。

之后单独改40GP不会偷偷改40HQ；旧推导会出现TWO_PRICE_DERIVATION_STALE，必须重新确认。新增推导规则需先实现确定性检查和测试，模型任意填写一个rule_id不能获得可信结果。

## 3. 日期、船期和航程

### 3.1 完整日期

`full_date`仅接受真实date或严格YYYY-MM-DD字符串；不接受datetime、月日、无前导零、非法日历或0000年份。

DateWindow是不可变日期区间，结束不能早于开始。`confirmed_month_day`要求明确传入已确认年份，没有“按当前年份补齐”的默认。跨年时分别确认两端年份；不因结束月日小于开始就擅自补一年。来源年证据ID必须能在可信上下文中找到。

### 3.2 日期适用性是三种结果

| 结果 | 含义 |
|---|---|
| MATCH | 请求日期口径与报价口径相同，起止完整，日期在包含边界的区间内 |
| OUTSIDE | 口径一致，日期明确超出至少一个已知边界 |
| UNCONFIRMED | 口径未知/不同，或缺边界且不能明确排除 |

例如报价适用订舱日，而用户仅提供ETD，即使月份看起来相同也不能返回已确认适用。口径未知时也不能按ETD日期判定过期。T26查询服务应分别展示已确认结果和待确认项。

### 3.3 周期船期不是真实航次

Schedule把星期去重并排序，严格接受整数1—7，拒绝bool和字符串数字；不推算下一班实际ETD。

- SINGLE必须恰有一个非负航程天数。
- ALTERNATIVES至少两个不同值，保留来源顺序，不转换为范围。
- CONFIRMED_RANGE必须恰有两个按大小排列的边界。
- UNKNOWN继续允许原文和未绑定备选值，含义未确认时不承诺航程。

路径仍保留UNKNOWN/DIRECT/TRANSSHIPMENT；两点直达和中转节点的结构约束沿用T02，不把路径空白认作直达。

## 4. 字段出处与可信上下文

### 4.1 出处一致性

非默认、非空业务字段必须有对应出处。可使用整个结构对象的出处，也可为有意义的命名子字段提供出处；数组按整体保存和确认。字段路径必须存在于QuotationValues，不允许用出处字典设置审核状态。

normalized_value必须与当前字段的JSON值及类型相同，不把True当作1，不把1.0当作1。UNKNOWN且为空表示已知缺失，可人工确认；UNKNOWN且有值仍阻止审核，置信度1也不能替代证据。

人工MANUAL出处要求recorded_by和带时区recorded_at，二者来自服务端可信会话和时钟。模型提取输出即使伪造这些字段，也会被ExtractionOutput拒绝；模型不能宣称自己进行了人工确认。

### 4.2 EvidenceContext

EvidenceContext由服务端从当前候选所属批次加载，不接受客户端或模型自建注册表作为证明，包含：

- evidence：证据ID到已验证Evidence对象的映射，key必须与对象ID一致。
- allowed_file_ids：当前批次允许的文件ID集合。
- condition_keys：当前上下文中已存在的条件键集合。

构造时复制并校验证据对象，冻结映射和集合。完整校验检查证据存在、文件属于当前批次、有效期年证据存在、条件键存在。证据的真实文件、单元格范围是否越界、图片尺寸及条件实际内容仍需T07/T18/T20加载和核对；有一个证据ID不表示OCR内容已经被证明正确。

来源EXPLICIT和RULE_DERIVED必须带证据。手工输入可不依赖附件，但须有人工身份、时间和审计事件。缺失币种不能从附加费USD反推；来源编码未制定继续NULL。

### 4.3 空值

备注、服务、价格口径、来源编码等可空字段使用None/JSON null，不接受空字符串或全空白字符串充当未知值。原文空白仍可保存在raw_payload或原始位置中，不自动伪造标准值。

## 5. 候选命令与审计意图

所有命令重验Candidate，防止Pydantic model_copy(update=...)或对象就地修改绕过基础校验。必须提供当前expected_version、服务端actor_id和带时区时间；应用结果已是APPLIED、NO_CHANGE、EXCLUDED的候选不能再直接修改。

每个实际变化返回CandidateChange：新的candidate及一个CandidateEvent。事件含操作者、UTC时间、前后完整JSON及其hash、变化字段。JSON字符串固定保存事件时的内容，不因后续对象修改而变化。无变化命令不产生事件或新版本。

这是待持久化的审计意图，不是已入库的audit_event。T12/T14应在同一事务中保存候选和事件；返回值本身不代表数据库写入成功。

### 5.1 编辑

`candidates.edit_candidate`遵守省略字段不改、明确null提出清空、结构对象整体替换的T02约定。每个变化字段记录人工出处，原始payload不覆盖；旧值与旧出处在事件before_json保留。

实际业务变更后：

1. version递增一次。
2. review_state变为PENDING_REVIEW。
3. review_version、reviewed_payload_hash、reviewed_by、reviewed_at清空。
4. 旧问题确认失效，重新检查；不能沿用上一次对缺失信息的确认。
5. 起运港、目的地或内部来源ID变化还将match_state重置UNMATCHED，避免继续使用来源范围已改变的匹配结论。

只修改价格不会自动改变另一个柜型的值。金额字符串表达、费用口径、备注等任何实际候选内容变化都重新审核，不试图静默判断“用户应该不在意”。

### 5.2 确认字段和纠正出处

- confirm_fields：人工明确确认屏幕上的字段及已知空值，生成MANUAL出处并进入待审核。禁止同时提交父对象和其子字段，避免相互覆盖。
- replace_provenance：可信服务纠正提取出处，验证字段值和证据范围。不能作为任意用户JSON直接调用的公开PATCH。仅改变出处也会增加版本、撤销旧批准。
- match_candidate：确认目的地必须提供从真实目录加载的有效Destination，禁止确认已停用目的地；保留唯一航线归属。匹配改变后重新审核，不自动应用报价。

### 5.3 审核

审核请求同时包含expected_version和用户预览的payload_hash，任一过时均拒绝。实际批准后review_version等于新候选version，保存规范payload hash、审核人和UTC时间；application_state仍为NOT_APPLIED。

审核迁移：

| 当前 | 允许下一状态 |
|---|---|
| PENDING_REVIEW | APPROVED / NEEDS_INFO / REJECTED |
| APPROVED | PENDING_REVIEW |
| NEEDS_INFO | PENDING_REVIEW |
| REJECTED | PENDING_REVIEW |

需要补充或已驳回的记录先重新打开或编辑，不能跳过重新核对直接批准。已批准记录要撤回也留下新事件，原批准事件保留。

任何未解决且影响REVIEW的Issue都会阻止批准；单纯ACKNOWLEDGED不解除它。其他已知限制可以明确确认后批准当前可知内容。例如目的地尚未确认时可以批准价格字段，但仍不能应用到正式库。

批准必须确认当前所有非INFO的未确认提示。确认只标记ACKNOWLEDGED并记录人和时间，不自动填值或把问题设为RESOLVED。不存在的问题代码拒绝确认，防止客户端用过时问题列表批准当前候选。

## 6. 按动作分开的缺失问题

IssueAction共用枚举为APPLY、COMPARE、EXPORT、REVIEW、DATE_FILTER，已生成前端类型。严重程度仅用于显示，affected_actions决定阻止的动作。

| 情况 | 审核 | 应用 | 比较/日期 |
|---|---|---|---|
| 无可信字段出处或出处不一致 | 阻止 | 阻止 | 阻止比较 |
| 非青岛或目的地未确认 | 可确认已知内容 | 阻止 | 阻止比较 |
| 没有任何明确柜型数值 | 可确认其他内容 | 阻止 | 阻止数值比较 |
| 指定柜型缺价 | 可审核其他柜型 | 其他有价柜型可保存 | 指定柜型不能比较，不拿其他柜型替代 |
| 币种未知 | 明确确认后可通过 | 保持NULL | 阻止比较 |
| 费用口径未知 | 明确确认后可通过 | 可保存 | 阻止宣称可比价格 |
| 完整有效期或适用口径缺失 | 明确确认后可通过 | 可作为日期未知记录保存 | DATE_FILTER提示待确认 |
| 船司或来源公开码未知 | 提示INFO | 可保存 | 不假定匹配具体船司 |

每次校验重新计算系统事实，不能通过把旧问题手写RESOLVED绕过。币种补齐后，旧CURRENCY_UNKNOWN自动退出当前问题列表；原问题及其确认仍在历史事件中。来源提出的其他自定义问题继续保留，不能通过系统重算全部删除。

候选本身不能直接作为正式Excel导出，EXPORT会提示FORMAL_EXPORT_REQUIRES_SNAPSHOT；T11必须从受控迁移后的正式版本快照生成六sheet文件。完整导出的权限及版本锁定不由一个候选门禁代替。

APPLY门禁仍不是实际应用：T17还须核对真实目录、船司/来源档案状态、条件、目标报价身份、选中版本、计划hash、数据集版本、事务和幂等。COMPARE也不是方案排名：T26还须核对跨记录币种、费用口径及适用条件，不能仅凭单条候选没有阻断就标最低价。

## 7. 其他状态表

- 匹配允许UNMATCHED、SUGGESTED、CONFIRMED、OUT_OF_SCOPE之间按明确确认重置；SUGGESTED不等于正式确认。
- 应用仅允许NOT_APPLIED进入APPLIED、NO_CHANGE或EXCLUDED，结果均为终态。失败记录写application/job，不新增一个混淆审核含义的FAILED候选状态。
- 计划仅允许DRAFT进入READY/STALE/CANCELLED，READY进入APPLIED/STALE/CANCELLED。过时、取消、已应用计划不再复用。
- 本任务只校验允许的迁移；实际计划生成和正式应用属于T15—T17，Worker状态和恢复由T07实现。

## 8. 后续持久化接入要求

1. T12/T14调用新领域命令，客户端不能直接提交actor、审批字段、状态或审计JSON作为可信结果。
2. 从会话和数据库加载候选、当前真实目录及EvidenceContext；旧版本先拒绝。一个请求内使用一致的上下文，不能查询一半后静默切换来源版本。
3. 在T05的unit_of_work中比较候选版本，保存新候选及事件；数据库竞争失败须整体回滚。纯函数通过不代表并发保存已成功。
4. **review_version映射须在T12接入时完成显式迁移**：领域合同用None表示没有当前审核快照；T05初版列为非空计数默认1。尚未接入候选写入服务，因此T06不冒险重建有外键引用的旧表；T12必须通过新增迁移统一可空语义，并验证带证据/修订引用的旧候选升级，不能用0、1或保留旧批准版本假装已清空。当前不存在将本任务返回值直接写入该列的业务接口。
5. 候选应用状态的持久化变更需保留原人工审批的业务内容及事件，不能将服务端记应用状态伪装成一次新的人工批准；T17按事务和版本合同设计适配。
6. 本任务不新增数据库表或修改已交付迁移。T05的SQLite结构版本仍是0002_history_guards，健康接口仍报告结构基础阶段T05；业务任务完成情况看任务计划和完成报告。
